05. 에러를 읽는 디버깅 루프

에러 전문과 재현 절차를 전달하고 추측 수정 대신 원인 로그 확인을 요구할 수 있다.

개념 읽기 → 실습 → 확인 문제 5개 모두 맞히기 → 튜터와 대화로 다지기

왜 여기서 막히나

오류가 발생했을 때 단순히 「안 돼요」라고 요청하면 AI는 화면을 보지 못하므로 엉뚱한 추측으로 멀쩡한 코드를 수정합니다. 수정이 반복될수록 코드는 누더기가 되고 원래 작동하던 부분까지 차례대로 고장 납니다. 오류 메시지 전체와 실행 환경을 있는 그대로 전달하는 방식이 디버깅의 출발점입니다. 같은 해결책이 세 번 연속 실패하면 대화를 멈추고 접근 경로를 전환해야 합니다.

핵심 개념 세 가지

  1. 3요소 보고디버깅을 요청할 때 재현 절차, 실제 에러 메시지 전문, 기대했던 정상 동작의 세 가지를 빠짐없이 제공하는 규칙입니다. AI가 문제 상황을 정확히 시뮬레이션할 수 있도록 환경 정보를 통제합니다. 주관적인 느낌 대신 객관적인 콘솔 로그를 그대로 복사해야 합니다.
  2. 원인 추적 로그 요구코드를 바로 고치지 말고 어디서 변수 값이 끊겼는지 확인하는 출력문부터 추가하도록 지시하는 기법입니다. 성급한 수정은 다른 부작용을 낳기 쉽습니다. 데이터의 실제 흐름을 터미널에 출력시켜 눈으로 확인한 뒤에 수정에 들어갑니다.
  3. 3회 실패 시 전환 규칙동일한 오류에 대해 AI의 수정 시도가 세 번 연속으로 실패하면 해당 세션을 즉시 중단하는 원칙입니다. /clear 명령어로 대화 맥락을 비우거나 다른 라이브러리 사용 등 근본적인 구조 변경을 검토합니다. 실패한 맥락이 길어질수록 AI는 잘못된 가정에 갇힙니다.

같은 일, 다른 요청

이렇게 요청하면

아까 알려준 코드 실행했는데 에러 나요. 안 되니까 다시 제대로 고쳐 줘.

이렇게 요청한다

스크립트 실행 중 에러가 발생했습니다. 아래 정보를 바탕으로 원인을 먼저 분석해 주십시오.

1. 실행 명령어: python script.py --input data.xlsx
2. 발생한 에러 전문:
FileNotFoundError: [Errno 2] No such file or directory: 'data.xlsx'
3. 기대한 동작: data.xlsx를 읽어 요약 보고서 텍스트를 터미널에 출력해야 합니다.

코드를 바로 수정하지 마십시오. 현재 스크립트가 바라보고 있는 작업 경로(os.getcwd())와 파일 존재 여부를 검사하는 로그를 먼저 추가해 주십시오.

단순한 불평 대신 실행 명령과 에러 전문을 정확히 제공하여 AI의 추측 범위를 좁혔습니다. 또한 성급한 코드 수정을 금지하고 현재 작업 경로를 확인하는 진단 코드를 먼저 요구하여 원인을 명확히 찾아냈습니다.

30분 실습

  1. 최근 작성한 스크립트나 웹페이지에서 일부러 오타를 내어 콘솔 에러를 발생시킵니다.
  2. 브라우저 개발자 도구(F12) 콘솔이나 터미널에서 붉은색 에러 텍스트 전문을 끝까지 복사합니다.
  3. 재현 경로, 에러 전문, 기대 동작의 3요소 형식에 맞추어 프롬프트를 작성해 전달합니다.
  4. AI에게 「코드를 바꾸지 말고 원인 파악을 위한 console.log 혹은 print문만 3군데 넣어줘」라고 요구합니다.

통과 기준

  • 「안 돼요」라는 표현을 쓰지 않고 에러 전문을 온전히 복사해 전달했습니다.
  • AI가 수정을 단행하기 전에 진단용 로그 코드를 먼저 작성하도록 통제했습니다.
  • 추가된 로그 출력을 통해 실제 어떤 데이터가 잘못 전달되었는지 확인했습니다.

확인 문제

다섯 문제를 모두 맞혀야 이 단계를 통과합니다. 틀리면 해설을 읽고 다시 풀면 되고, 다시 풀 때마다 문제와 보기 순서가 바뀝니다.

튜터와 다지기

문제를 맞혔어도 내 프로젝트에서 바로 쓰지 못하면 아직 아는 것이 아닙니다. 아래 프롬프트를 Claude에 붙여 넣으면 「통과」라고 할 때까지 내 상황에 맞춘 질문을 계속 받습니다.

너는 내 바이브 코딩 튜터다. 나는 「에러를 읽는 디버깅 루프」 단계를 공부하고 있다.
이 단계의 목표는 「에러 전문과 재현 절차를 전달하고 추측 수정 대신 원인 로그 확인을 요구할 수 있다.」
다룰 개념은 「3요소 보고」, 「원인 추적 로그 요구」, 「3회 실패 시 전환 규칙」이다.

규칙
1. 설명부터 하지 말고, 내가 지금 만드는 프로젝트가 무엇인지 먼저 한 가지만 묻는다.
2. 질문은 한 번에 하나씩. 내 프로젝트 상황에 맞춘 문제를 낸다.
3. 내가 틀리면 정답을 바로 말하지 말고 힌트를 하나 준 뒤 다시 묻는다.
4. 개념마다 내가 실제로 보낼 프롬프트를 직접 써 보게 하고, 부족한 점을 고쳐 준다.
5. 서로 다른 상황 문제 세 개를 연속으로 맞히면 「통과」라고 말하고, 아직 약한 부분을 한 줄로 알려 준다.
6. 통과하기 전에는 다음 단계로 넘어가지 않는다.
