07. 계획 모드와 안전한 코드 개선

계획 모드를 이용해 여러 파일을 수정하기 전에 변경 순서를 확인하고 기능 변경 없는 코드 정리를 수행할 수 있다.

개념 읽기 → 실습 → 요점 카드 모두 「안다」 → 튜터와 대화로 다지기

왜 여기서 막히나

한 줄 요청으로 코드를 고치다 보면 Claude Code가 의도하지 않은 여러 파일을 한꺼번에 수정하여 기존 기능이 망가집니다. 비개발자는 어떤 파일이 왜 바뀌었는지 검토하지 못해 이전 상태로 되돌리지 못하고 막힙니다. 기능 추가와 코드 정리를 동시에 요청하여 오류의 원인을 찾지 못하는 상황도 자주 발생합니다. 파일이 늘어나는 단계에서는 작업을 분리하고 변경 순서를 먼저 확인하는 작업 방식이 필요합니다.

핵심 개념 세 가지

  1. 계획 모드Shift+Tab을 누르면 Claude Code가 파일을 직접 수정하지 않고 변경 계획만 수립하는 계획 모드로 전환됩니다. 여러 파일이 연관된 큰 수정 작업을 할 때 변경할 파일 목록과 수정 순서를 먼저 문서 형태로 확인하고 승인할 수 있습니다. 계획 모드에서 작성된 절차를 사람이 검토한 뒤 일반 모드로 돌아와 안전하게 실행합니다.
  2. 리팩터링의 원칙리팩터링은 외부에서 보이는 프로그램의 동작을 전혀 바꾸지 않으면서 내부 코드 구조만 읽기 쉽고 관리하기 편하게 바꾸는 작업입니다. 새로운 기능을 추가하는 작업과 기존 코드를 정리하는 작업을 같은 프롬프트에서 함께 지시하면 안 됩니다. 기존 기능이 정상 작동하는 상태를 git 커밋으로 저장한 뒤 독립된 단계로 코드 정리만 진행합니다.
  3. 세 번 규칙비슷한 코드가 두 번 나타날 때까지는 개별 코드로 유지하고 세 번째로 중복될 때 하나의 공통 함수나 컴포넌트로 묶는 설계 원칙입니다. 초기에 성급하게 공통 함수로 만들면 나중에 화면마다 세부 요구사항이 달라질 때 오히려 코드가 복잡해집니다. 실제로 세 곳 이상에서 완전히 같은 처리를 수행할 때 비로소 추출을 요청합니다.

같은 일, 다른 요청

이렇게 요청하면

코드가 너무 길고 복잡한데 알아서 깔끔하게 정리해주고 새 페이지도 하나 추가해줘.

이렇게 요청한다

현재 프로젝트에서 새로운 기능은 일절 추가하지 않고 리팩터링만 진행합니다.
먼저 Shift+Tab을 눌러 계획 모드 상태에서 답변을 주십시오.

[목표]
js/main.js 파일에서 공지사항 목록을 화면에 그리는 함수와 보도자료 목록을 화면에 그리는 함수가 거의 동일한 구조를 가지고 있습니다.

[작업 요구사항]
1. 두 함수에서 중복되는 HTML 렌더링 부분을 별도의 재사용 가능한 함수로 분리합니다.
2. 분리된 함수는 js/render.js 파일로 생성하고 기존 main.js에서 불러와 사용하도록 변경합니다.
3. 기존 화면의 동작, CSS 클래스명, 출력 결과는 단 1픽셀도 바뀌지 않아야 합니다.

파일을 직접 수정하기 전에 어떤 순서로 파일을 나눌 것인지 계획 목록을 먼저 보여주십시오.

새 기능 추가와 코드 정리를 엄격하게 분리하여 기존 기능의 훼손 위험을 차단했습니다. 계획 모드를 지정하여 AI가 파일을 즉시 수정하지 않고 먼저 사람이 수정 범위를 검토할 수 있도록 통제권을 확보했습니다.

30분 실습

  1. 현재 본인이 운영하는 홈페이지 프로젝트 폴더에서 git status를 실행해 변경 사항이 없도록 커밋합니다.
  2. Claude Code 입력창에서 Shift+Tab을 눌러 계획 모드로 전환한 뒤 가장 긴 자바스크립트 파일의 중복 코드 분석을 요청합니다.
  3. Claude Code가 제안한 계획 단계에서 기존 동작의 변경이 없는지 읽어보고 승인합니다.
  4. 일반 모드로 복귀하여 계획에 따라 함수를 분리하게 하고 브라우저를 새로고침하여 이전과 완전히 똑같이 동작하는지 검증합니다.

통과 기준

  • 새로운 파일로 함수를 분리한 후에도 브라우저 개발자 도구 콘솔에 빨간색 오류 메시지가 없습니다.
  • 리팩터링 전후의 화면 요소 배치와 기능 동작이 완벽하게 일치합니다.
  • git diff 명령을 실행했을 때 새로운 기능 로직 없이 코드 구조 이동만 기록되어 있습니다.

요점 카드

질문을 보고 답을 먼저 떠올린 뒤 눌러서 확인합니다. 답을 보지 않고 말할 수 있는 카드에만 「안다」를 표시하고, 모든 카드에 표시하면 이 단계를 통과합니다.

  1. 계획 모드로 전환하는 단축키는?

    Shift+Tab을 누릅니다. 파일을 직접 수정하지 않고 변경 계획과 수정 순서를 먼저 문서 형태로 작성합니다.

  2. 외부 동작을 바꾸지 않고 내부 코드 구조만 정리하는 작업 명칭은?

    리팩터링입니다. 새로운 기능 추가 프롬프트와 분리하여 독립된 단계로 진행해야 합니다.

  3. 비슷한 코드를 공통 함수로 묶는 시점의 기준은?

    세 번 규칙에 따라 세 번째로 중복이 나타날 때 묶습니다. 두 번 겹칠 때 성급하게 묶으면 이후 개별 화면 요구사항 변경에 대응하기 어렵습니다.

  4. 리팩터링 직후 의도치 않은 코드 변경이나 삭제를 확인하는 명령어는?

    git diff입니다. 수정된 줄을 대조하여 기존 화면 로직이나 보조 파일이 훼손되지 않았는지 확인합니다.

  5. 리팩터링을 시작하기 전에 정상 작동 상태를 보존하기 위해 실행하는 명령어는?

    git status로 변경 사항을 확인하고 git commit을 실행합니다. 정상 작동 상태를 커밋으로 저장해 두어야 오류 발생 시 안전하게 복구할 수 있습니다.

  6. 계획 모드를 사용하기에 가장 적절한 작업 규모의 기준은?

    여러 파일에 걸쳐 데이터 흐름이나 화면 표시 규칙이 함께 바뀌는 작업입니다. 단일 파일의 단순 오탈자 수정이나 스타일 변경에는 계획 모드를 쓰지 않아도 됩니다.

튜터와 다지기

문제를 맞혔어도 내 프로젝트에서 바로 쓰지 못하면 아직 아는 것이 아닙니다. 아래 프롬프트를 Claude에 붙여 넣으면 「통과」라고 할 때까지 내 상황에 맞춘 질문을 계속 받습니다.

너는 내 바이브 코딩 튜터다. 나는 「계획 모드와 안전한 코드 개선」 단계를 공부하고 있다.
이 단계의 목표는 「계획 모드를 이용해 여러 파일을 수정하기 전에 변경 순서를 확인하고 기능 변경 없는 코드 정리를 수행할 수 있다.」
다룰 개념은 「계획 모드」, 「리팩터링의 원칙」, 「세 번 규칙」이다.

규칙
1. 설명부터 하지 말고, 내가 지금 만드는 프로젝트가 무엇인지 먼저 한 가지만 묻는다.
2. 질문은 한 번에 하나씩. 내 프로젝트 상황에 맞춘 문제를 낸다.
3. 내가 틀리면 정답을 바로 말하지 말고 힌트를 하나 준 뒤 다시 묻는다.
4. 개념마다 내가 실제로 보낼 프롬프트를 직접 써 보게 하고, 부족한 점을 고쳐 준다.
5. 서로 다른 상황 문제 세 개를 연속으로 맞히면 「통과」라고 말하고, 아직 약한 부분을 한 줄로 알려 준다.
6. 통과하기 전에는 다음 단계로 넘어가지 않는다.
